## Commands

```bash
npm start              # expo start (dev server)
npm run ios            # expo run:ios
npm run android        # expo run:android
npm run web            # expo start --web

npm test               # jest (all tests)
npm run test:watch     # jest --watch
npx jest src/utils/__tests__/paywallCalc.test.ts   # single test file
```

- `ios/` and `android/` are gitignored — they're generated by `expo prebuild`, not hand-maintained. Don't rely on edits to native project files surviving a prebuild.
- No lint script is configured in this repo.
- Builds/releases go through EAS (`eas.json`: `development`, `preview`, `production` profiles). The `eas-build-pre-install` hook runs `scripts/check-prod-keys.js`, which aborts a `production`-profile build if `EXPO_PUBLIC_RC_IOS_KEY` / `EXPO_PUBLIC_RC_ANDROID_KEY` / `EXPO_PUBLIC_SENTRY_DSN` are still placeholders — a guard against shipping a build with no real RevenueCat/Sentry keys.
- `runtimeVersion.policy` is `"appVersion"` (`app.json`), so an OTA update (`eas update`) only reaches installs whose native binary has the exact same `expo.version`. A JS-only fix meant to reach an already-shipped version must **not** bump `version` — doing so silently cuts that OTA off from every existing install. Only bump `version` when the change requires a new store submission (native module change, or you specifically want the update gated to a new build).
- **Local dev-client on iOS Simulator can fail to connect to Metro with no useful error** (`Failed to connect to http://...`, tried against `localhost`, LAN IP, `--offline`, `--localhost`, all identically). Two separate, stackable causes, both silent:
  1. `app.json`'s `updates.codeSigningCertificate` (`./certs/certificate.pem`) makes the dev client require a *signed* manifest even for local dev, but the matching private key is intentionally not in the repo. Symptom in the Metro log (only visible when NOT passing `--offline`): `CommandError: Must specify --private-key-path argument to sign development manifest for requested code signing key`.
  2. iOS's Local Network Privacy: without `NSLocalNetworkUsageDescription` (+ `NSBonjourServices: ["_expo._tcp"]`) in `ios.infoPlist`, iOS never shows a permission prompt and just silently blocks the dev client's connection to Metro — check **Settings → Privacy & Security → Local Network** in the Simulator; if the app isn't even listed there, this is the cause.
  - Fix for a local debugging session: temporarily remove `codeSigningCertificate`/`codeSigningMetadata` and add the two Info.plist keys above to `app.json`, then `npx expo prebuild --clean && npx expo run:ios` (Info.plist changes need a native rebuild, not just a Metro restart). **Revert both before committing** — they must not ship (code signing is a real production control; the Local Network permission has no purpose in production and would show users an unexplained privacy prompt).

## Architecture

**FX Trade Journal** — an Expo/React Native app (expo-router, TypeScript strict mode) for logging and reviewing forex trades. `app/` holds file-based routes; `src/` holds the actual logic.

- **Routing**: `app/(tabs)/` (index/calendar/monthly/yearly/stats/bookmarks/settings) is the main tab group; `app/trade/new.tsx` and `app/trade/[id].tsx` are modal screens for creating/viewing a trade; `app/onboarding.tsx`, `app/paywall.tsx`, `app/calculator.tsx` (position size calculator), and `app/badges.tsx` (achievement badges) are also modal/standalone routes. `app/_layout.tsx` is the entry point: it opens the DB, loads settings, initializes purchases, and gates rendering behind `AppLockGate` and `ErrorBoundary`.

- **Data layer** (`src/db/`): local SQLite via `expo-sqlite`, encrypted with SQLCipher.
  - `database.ts` handles a one-time migration from the old plaintext DB (`fx_journal.db`) to the encrypted DB (`fx_journal_v2.db`) using `ATTACH ... KEY` + `sqlcipher_export()` (page-level copy doesn't work between plaintext/encrypted SQLCipher files). A `SecureStore` flag (`fx_db_migrated_v1`) marks completion; `resetDatabase()` is the last-resort recovery path if the key/DB become inconsistent.
  - Schema changes are applied as a running list of `ALTER TABLE` statements (`SCHEMA_MIGRATIONS` in `database.ts`, no migration framework/versioned files) — there is no rollback, only additive `ADD COLUMN` migrations. `initializeDatabase()` tracks progress via `PRAGMA user_version`, running only the slice past the DB's current version (each statement is still guarded by catching "duplicate column name", since a DB from before this versioning existed has `user_version` unset and re-runs the full list once, harmlessly). `src/utils/backup.ts` imports `SCHEMA_MIGRATIONS.length` directly for its backup-file `schema` field, so the two can no longer drift out of sync.
  - `dbEncryption.ts` stores the SQLCipher passphrase in `SecureStore` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` (excluded from iCloud backup, device-only).

- **Image storage** (`src/utils/imageStorage.ts`): trade chart images are copied into `documentDirectory/charts/` and stored in the DB as **relative** paths (`charts/xxx.jpg`), resolved to an absolute URI only at read time. This is because `documentDirectory`'s container ID changes across reinstalls/OS updates, which would silently break absolute paths. Old absolute-path rows are migrated to relative paths in `database.ts`.

- **State**: Zustand stores in `src/store/` — `tradeStore.ts`, `settingsStore.ts`, `purchaseStore.ts`. No React Context/Redux.

- **Monetization** (`src/store/purchaseStore.ts`): RevenueCat (`react-native-purchases`), entitlement id `premium` — `hasPremium()` checks `ENTITLEMENT_IDS` (`['premium', 'FXトレード日記 Pro']`) so a RevenueCat-dashboard rename doesn't silently break premium detection the way the non-ASCII-only id did once before. The dashboard must have a `premium` entitlement configured (in addition to, or eventually instead of, the legacy Japanese-name one) for this to take effect. Both this and Sentry init (`app/_layout.tsx`) check for placeholder API keys (`isPlaceholderKey`/`isPlaceholderDsn`, matching `/xxxx/i`) and skip initialization when unset, so local dev works without real keys in `.env`. Required env vars (read via `process.env.EXPO_PUBLIC_*`): `EXPO_PUBLIC_RC_IOS_KEY`, `EXPO_PUBLIC_RC_ANDROID_KEY`, `EXPO_PUBLIC_SENTRY_DSN`.

- **App lock** (`src/components/AppLockGate.tsx`): biometric lock via `expo-local-authentication`, gated on `AppState` changes. Guards against the OS's own biometric prompt UI (which transiently backgrounds the app) being mistaken for a real background/foreground transition and triggering a re-auth loop.

- **i18n** (`src/i18n/`): a small hand-rolled `t()`/`tArr()` implementation, not i18next. Supports 11 languages (`ja` default fallback, `en`, `de`, `fr`, `es`, `it`, `id`, `tr`, `hi`, `vi`, `pt`). Device locale is detected once at module load (`src/i18n/index.ts`), not reactively — changing the OS language requires an app restart to take effect.

- **CSV import** (`src/utils/mt4Import.ts`): parses MT4 (tab/comma-delimited) and MT5 (comma-delimited "Deals") trade history exports.

- **Marketing/legal site**: the repo root also contains a static landing page and legal pages (`index*.html`, `privacy-policy-*.html`, `terms-*.html`, `support-*.html`, `lp-assets/`) in the same 11 languages as the app, deployed independently of the Expo app. CI (`.github/workflows/lp-checks.yml`) validates these with `html-validate` and a non-blocking Lighthouse report, triggered only on changes to `*.html`/`manifest.json`/`lp-assets/**`. `.github/workflows/npm-audit.yml` runs `npm audit --audit-level=high` on every push but with `continue-on-error: true`, since flagged vulnerabilities are in build-only tooling (Expo CLI, jest-expo, etc.) that never ships in the app bundle.

- **iOS home screen widget** (`targets/widget/`): a WidgetKit extension (SwiftUI, `FXWidget.swift`) added via the `@bacons/apple-targets` config plugin, which links `targets/widget/` into the Xcode project on every `expo prebuild` (survives regeneration, unlike hand-editing `ios/`). Shows this month's win rate and total pips.
  - **Data flow**: `src/utils/widgetSync.ts`'s `syncWidgetData()` — called from `app/_layout.tsx` on launch and from `tradeStore.ts`'s `addTrade`/`editTrade`/`removeTrade` — recomputes the current calendar month's stats (independent of whatever month the UI happens to be browsing) and writes already-`t()`-translated label strings into the shared App Group container via `ExtensionStorage.set()`, then calls `ExtensionStorage.reloadWidget()`. The Swift side has no i18n of its own — it only renders whatever strings it's given.
  - Widget text is hardcoded to white — the widget's own background (`$widgetBackground` in `expo-target.config.js`) is a fixed dark color, but SwiftUI's `.primary`/`.secondary` foreground styles follow the *system* light/dark setting, not the widget's own background, so on a light-mode device they render near-black text on a dark background and become unreadable.
  - `app.json`'s `ios.appleTeamId` must be set (it's the `OU` field of the dev certificate: `security find-certificate -c "Apple Development: <name>" -p | openssl x509 -noout -subject`) or the plugin warns and widget builds may fail signing.
  - **Known gap**: as of this writing, a local `expo prebuild && expo run:ios`/`xcodebuild` (Simulator, ad-hoc "Sign to Run Locally" identity, no real device) produces a build where **both** the main app's and the widget's actual signed entitlements come out empty (verified via `codesign -d --entitlements :- FX.app`) — App Groups silently doesn't work end-to-end locally, even though the source `.entitlements` files are correct and `CODE_SIGN_STYLE=Automatic`/`ios.appleTeamId` are set. This is very likely because the `com.fxtradejournal.ios` App ID has never had the App Groups capability registered against it on Apple's servers — that registration normally happens the first time someone checks "App Groups" in Xcode's Signing & Capabilities tab (or via developer.apple.com directly), which requires a live, authenticated Apple Developer session and can't be done from the CLI. EAS Build's managed credentials service is expected to handle this automatically and may not hit the same issue — this needs verification on a real EAS build or device run, not just Simulator.
